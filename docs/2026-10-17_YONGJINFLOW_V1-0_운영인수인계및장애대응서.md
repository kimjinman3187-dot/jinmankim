## 1. 시스템 구성

| 영역 | 운영 자산 | 역할 |
|---|---|---|
| 화면 | GitHub Pages | 정적 HTML·CSS·JavaScript 제공 |
| 배포 | `.github/workflows/pages.yml` | `main` push 시 Pages 자동 배포 |
| 로그인 | Firebase Authentication | 승인된 Google 계정 인증 |
| 업무 데이터 | Cloud Firestore | 사용자·주문·결재·생산·재고·이력 저장 |
| 첨부 | Firestore 분할 첨부 및 기존 Storage 경로 | Spark 문서 첨부·무결성 검증, 기존 승인 첨부 호환 |
| 권한 | `firestore.rules`, `storage.rules` | 역할·소유권·상태 전이·불변 필드 강제 |
| 기준 소스 | GitHub `main` | 운영 배포 원본 |

`functions/`에는 과거·호환 구현과 테스트 자산이 남아 있으나, v1.0 표준 결재 핵심 흐름은 Spark 제약에 맞춘 클라이언트 트랜잭션과 Firestore Rules를 기준으로 한다. Functions 배포 여부를 임의로 변경하지 않는다.

## 2. 일상 운영 절차

### 업무 시작 전

1. 운영 URL이 열리고 로그인 화면이 표시되는지 확인한다.
2. 본인 계정명과 역할이 맞는지 확인한다.
3. 화면에 `internal`, `permission-denied`, 무한 로딩이 보이면 업무 입력을 반복하지 말고 장애 절차를 따른다.

### 역할별 핵심 업무

- 영업: 주문 등록·조회, 미수금 확인
- 회계: 회계·입금·지급·ERP 파일 처리
- 생산: 주문 생산수량과 생산 단계 처리
- 생산관리자: 재고 생산, 입고, 주문 배정, 출고, 반품, 정정
- 관리자: 결재·사용자 승인·전사 현황과 위 업무의 관리

세부 사용 순서는 `2026-10-17_YONGJINFLOW_V1-0_현장사용자_1페이지SOP.md`를 따른다.

## 3. 계정 추가·변경 절차

1. 회사에서 사용할 Google 계정과 부여할 역할을 Gene이 확정한다.
2. 사용자가 운영 URL에서 Google 인증을 1회 시도하거나 관리자가 Firebase Authentication에서 계정을 확인해 Auth UID를 확보한다. 이 단계에서는 `users/{uid}` 미등록으로 업무 화면 접근이 제한될 수 있다.
3. 관리자가 해당 UID의 `users/{uid}` 문서에 이름, 역할, `status=active`, 인증 UID를 정확히 등록한다.
4. 결재자로 사용할 회계·관리자는 `business_approver_directory/{uid}`도 별도 승인 후 등록한다.
5. 사용자 등록 완료 후 다시 로그인해 역할별 메뉴와 허용·거부 작업을 1회 확인한다.

`users`, 결재자 명단, Auth 설정을 직접 수정하는 작업은 Gene 승인 없이 수행하지 않는다. 퇴직·휴직자는 삭제보다 `status` 정지를 우선 검토해 이력을 보존한다.

## 4. 정상 배포 절차

### 정적 화면·코드·문서

1. `origin/main`을 갱신하고 새 `codex/` 작업 브랜치를 만든다.
2. 변경 예정 파일과 금지 범위를 기록한다.
3. 자동 테스트와 실제 화면을 확인한다.
4. 관련 파일만 커밋·푸시하고 PR의 Files changed를 검토한다.
5. 승인 후 `main`에 병합한다.
6. GitHub Pages 최신 build가 `built`이고 대상 SHA와 일치하는지 확인한다.
7. 운영 URL에서 캐시를 새로고침하고 핵심 화면을 점검한다.

### Firestore/Storage Rules

1. Gene의 명시적 배포 승인을 받는다.
2. 현재 운영 Ruleset과 대상 프로젝트 `yongjin-enterprise`를 확인·백업한다.
3. Emulator에서 허용·거부·상태 전이 테스트를 통과시킨다.
4. Rules diff와 대상 프로젝트를 다시 확인한다.
5. Rules만 제한 배포하고 관리자 계정으로 스모크 테스트한다.

로컬 Firebase CLI 기본 프로젝트를 신뢰하지 않는다. 모든 명령에서 `yongjin-enterprise`를 명시한다.

## 5. 배포 후 필수 확인

- GitHub Pages build 상태와 commit SHA 일치
- 로그인 후 Console 치명 오류 없음
- 업무 홈·결재·영업·회계·생산·재고 화면 진입
- 문서 조회 실패를 `0건`으로 잘못 표시하지 않음
- 생산·재고 현재고·예약·가용 수량 표시
- 첨부 완료 상태와 검증 다운로드
- A4 요약본에 문서정보와 결재칸 표시

운영 데이터로 승인·지급·출고 버튼을 시험하지 않는다. 쓰기 검증은 명시된 테스트 데이터와 승인된 계정으로만 수행한다.

## 7. 증거 수집

장애 신고에는 다음 내용을 남긴다.

- 발생 시각과 사용자 역할
- PC/모바일, 브라우저 이름과 화면 주소(`#docbox`, `#factory` 등)
- 실행한 동작과 기대 결과
- 화면 전체 캡처와 표시된 오류 문구
- 가능하면 개발자도구 Console 오류
- 관련 문서번호·주문번호·품목코드(비밀번호·인증토큰 제외)

Google 비밀번호, Firebase 토큰, 개인 키, 계좌 비밀번호를 문서·메신저·GitHub에 남기지 않는다.

| 중복 입금·ERP 우려 | operation ID, 이체번호, ERP 상태 | 재실행 전 기존 이력 확인. 취소·정정·재처리 흐름 사용 |
